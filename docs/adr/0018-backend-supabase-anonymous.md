## 배경

공유 데이터(ADR-0017)에는 계정, "내 항목만 수정", 서버 검증·빈도 제한, 신고 집계, 관리자 로그인이 필요하다. 일반 사용자에게는 로그인 화면이 없어야 하고(D17), 계정은 첫 쓰기 때 만든다(Y-A1, Q-Y10). 관리자는 익명이 아닌 별도 로그인이어야 한다(Y-R5) — 익명 기기 계정은 기기를 잃으면 사라진다. 비용은 무료 또는 저비용.

## 결정

1. **Supabase**(Postgres + Auth + PostgREST + Cron, 도쿄 리전)를 쓴다. 가중 비교 Supabase 92, Firebase 72, Cloudflare D1+Workers 57, PocketBase 47 (tech-stack-v2 §5.3).
2. **일반 사용자 = 익명 계정, 첫 쓰기 때 생성.** 앱은 읽기에 계정을 쓰지 않는다(`anon` + publishable 키). 등록·신고 버튼을 처음 누르면 `signInAnonymously()` 후 RPC 를 부른다. 세션은 `localStorage` 키 `yui.auth`. 익명 사용자는 `authenticated` 역할이므로 **익명 여부로 권한을 나누지 않고**, 권한은 RPC 안의 소유·정지 검사와 관리자 허용 목록으로만 판단한다.
3. **관리자 = 이메일+비밀번호 + TOTP(aal2) + 허용 목록(`app.admins`).** `[보안 검토 #3·#4·#5·낮음 반영, 2026-10-12]`
   - **생성:** 이메일 공급자의 공개 가입은 끈다. 책임자가 `app.admin_invites` 에 이메일을 넣고 → 대시보드 또는 Admin API 로 사용자를 만들고 → 생긴 `user_id` 로 `app.admins` 행을 넣는다. 가입 훅은 `admin_invites` 만 본다. (첫 판은 훅이 `admins(user_id FK)` 를 사용자가 생기기 **전에** 확인하려 해 관리자를 만들 수 없었다.)
   - **연결은 생성 호출이 돌려준 id 로만** `[재검토 #2]`: 익명 사용자가 책임자보다 먼저 `updateUser({email})` 로 초대 이메일을 걸 수 있으므로 이메일로 사용자를 찾아 연결하지 않는다. `app.bind_admin(id, email)`(postgres 전용)이 비익명·이메일 확인·이메일 일치·초대 뒤 생성·초대 미사용·같은 이메일의 다른 사용자 없음을 확인한 뒤에만 `admins` 행을 넣는다.
   - **SMTP** `[재검토 #4]`: 익명 사용자의 이메일 연결 요청도 프로젝트 기본 SMTP(시간당 몇 통)를 소모해 관리자 비밀번호 재설정 메일을 막을 수 있다 — 관리자 1명이면 대시보드 직접 재설정 런북, 2명 이상이면 사용자 SMTP. **책임자 결정 D25(관리자 1명)·D26(SMTP 설정은 출시 전 항목으로 미룸)** — 런북 R-6 으로 운영하고 사용자 SMTP 여부는 출시 전에 정한다(RFC-0003 §17.6a PL-2).
   - **권한의 근거는 `admins` 행뿐.** 익명 사용자는 `updateUser({email})` 로 훅을 거치지 않고 비익명이 될 수 있으므로 "비익명 = 허용 목록" 가정을 버렸다.
   - **TOTP 는 책임자가 계정을 만들 때 등록**한다 — 첫 로그인 때 등록하게 하면 비밀번호가 샌 공격자가 먼저 자기 TOTP 를 등록할 수 있다. **D25 로 관리자는 책임자 본인 1명**이므로 "등록해 넘기는" 단계는 없고, 책임자가 생성 직후 자기 TOTP 요소를 **2개**(주 + 예비) 등록한다. Supabase 에는 백업 코드가 없고 공식 문서는 두 번째 TOTP 요소를 복구 수단으로 안내한다(최대 10개, 2026-10-12 확인). 둘 다 잃으면 대시보드에서 비밀번호 교체 → secret 키로 `auth.admin.mfa.deleteFactor` → 재등록(RFC-0003 §17.7 R-7).
   - **`require_admin()` 은 실패 안전:** 클레임·세션 행이 없거나, `aal2` 가 아니거나, 세션 생성 12시간이 지났거나, `admins` 행이 없으면 **예외**. 모든 `admin_*` 의 첫 문장이 `perform app.require_admin()`. 세션 최대 수명·비활동 제한은 Pro 기능으로 보이므로(검토의 확인) **무료 플랜에서는 이 12시간 검사가 유일한 서버 측 만료**다.
   - **CAPTCHA 스위치를 켜면 비밀번호 로그인에도 적용**되므로 콘솔에 Turnstile 위젯과 CSP 허용을 둔다(ADR-0020).
   - 이메일은 관리자만 저장한다(Y-P1).
4. **키:** 클라이언트에는 publishable 키(`sb_publishable_…`)만. secret 키는 GitHub Actions 비밀값(감시·백업)에만. 레거시 `anon`/`service_role` 키는 비활성화(2026년 말 폐기 예정 — 공식 문서).
5. **가명 ID:** 관리자에게는 uuid 가 아니라 `accounts.ref`(첫 쓰기 때 만든 난수, `a-xxxxxxxxxx`)를 보인다. 계정 정지(Y-R7)는 이 값으로 한다(Y-P2, Q-Y11).
6. **익명 계정 정리:** Supabase 에 자동 정리가 없으므로(공식 문서) Cron 작업이 쓰기·신고 기준 1년 비활동 계정을 지운다(Y-P5). 소유 행만 cascade 로 사라지고 장소는 남는다.
7. **자동화된 대량 생성 대응(Y-A4, Y-S7):** Supabase 의 IP 당 익명 로그인 한도(기본 시간당 30 → **150 으로 올림** — 기숙사 NAT, 범위별 설정이 확인되지 않아 전체 값 `[검토 #6]`), 훅의 전역 시간당 한도(기본 200 — 익명 가입에 훅이 도는지는 미확인), **그와 무관한 보장으로 `require_writer` 가 앱 계정 생성 수를 시간당 200 으로 제한**(계정은 첫 쓰기 때만 생기므로 Auth 와 상관없이 대량 생성 계정의 쓰기를 막는다 `[재검토 #1]`), 공격 시 켜는 CAPTCHA 스위치(Turnstile, 기본 OFF, 사이트 키는 빌드에 미리 포함). 전역 한도 소진(DoS)은 감시 경보 → CAPTCHA ON 런북으로 대응 `[검토 #11]`. 사람 단위의 다중 계정은 막지 않는다(D20).

## 고려한 대안

| 대안 | 기각 이유 |
|---|---|
| Firebase (Auth + Firestore) | 익명 인증은 좋지만 빈도 제한·집계·자동 숨김을 규칙만으로 쓰기 어렵고 Functions 범위가 자료마다 상충. 이전 설계 재사용 불가 |
| Cloudflare D1 + Workers | 무료 한도 넉넉하지만 인증을 직접 구현. 권한이 모두 애플리케이션 코드 |
| PocketBase | 익명 로그인 기본 기능을 확인 못 함, 서버 운영 부담 |
| 앱을 열 때 익명 계정 생성 | Y-A1/Q-Y10 이 첫 쓰기로 정함. 읽기만 하는 사람의 MAU·DB 행이 생기지 않고, Auth 장애·한도가 읽기에 영향을 주지 않는다 |
| 관리자 = 익명 계정을 SQL 로 승격 | 기기를 잃으면 관리자도 사라진다(Y-R5 의 이유). 2단계 인증 불가(Y-S3) |
| 관리자 이메일 OTP / 매직 링크 | 메일 발송(SMTP) 설정이 필요. 비밀번호+TOTP 는 메일 없이 2단계를 만족. 비밀번호 재설정만 메일이 필요 — 관리자 1명이면 책임자가 대시보드에서 처리 |

## 결과

- 좋은 점: 로그인 화면 없음, 읽기는 계정·Auth 와 무관, 관리자는 2단계 + 서버 세션 만료. 이전 조사(키 체계, GRANT 명시, 정의자 함수 규칙)를 그대로 쓴다.
- 나쁜 점: 무료 플랜은 백업이 없고 1주 비활동 시 일시정지(ADR-0022 가 대응). 저장소를 지우면 익명 계정을 잃는다(Y-A2 안내). 기숙사가 공인 IP 하나를 공유하면 IP 한도에 걸릴 수 있다(RFC-0003 OQ-5).
