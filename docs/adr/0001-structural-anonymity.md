## 배경

이 제품은 공동생활 공간의 익명 게시판이다(PRD §2-4). README 는 "익명성은 화면 처리가 아니라 구조"라고 하고, `schema.sql` 은 본문과 작성자를 다른 테이블에 두고 작성자 테이블을 "RLS 활성 + 정책 0개"로 만들었다. 그러나 현행 스키마에는 이 구조를 우회하는 경로가 여럿 있다.

- `exchange_requests.to_user` 와 오류 메시지로 작성자 동일성 판별 (S-2)
- `my_contacts.id`, `places.added_by`, `events.created_by` 로 uuid 대조 (N-6)
- Supabase 기본 권한 때문에 `anon` 에 함수 EXECUTE 잔존 (N-1)
- `is_admin` 자기 승격 후 운영자 정책으로 숨긴 글까지 읽기 (S-1)

또 "누구에게 익명인가"가 문서에 정의되어 있지 않다. 프로젝트 소유자는 SQL 편집기로 작성자 테이블을 읽을 수 있다.

## 결정

1. **본문·작성자 분리와 무정책 RLS 를 유지한다** (I-1, I-2). 작성자 테이블에는 `anon`/`authenticated` 테이블 권한도 주지 않는다(정책 0 + GRANT 0, 이중).
2. **클라이언트가 받는 어떤 응답에도 다른 사용자의 uuid 를 넣지 않는다** (I-6). uuid 컬럼은 컬럼 GRANT 에서 빼고, 사람을 가리키는 참조는 대리 키(`exchanges.id` 등)로 한다.
3. **작성자를 조회하는 정의자 함수는 작성자 값을 반환하지 않고, 결과·오류를 대상과 무관하게 균일화한다** (PR-10).
4. **권한은 마이그레이션이 전부 명시한다.** 마지막 단계에서 `anon`/`authenticated` 권한을 모두 회수한 뒤 필요한 것만 다시 주고, 점검 쿼리가 실패하면 마이그레이션을 실패시킨다(ERD §7 `0014`, `0016`).
5. **익명성의 범위를 명시한다:** 클라이언트(운영자 포함, 신뢰 경계 0·1)에게 익명. 프로젝트 소유자(경계 3)는 기술적으로 열람 가능하며, POL-1-4 의 사유로만 조회하고 기록한다. 이 범위를 개인정보처리방침에 쓴다(열린 질문 R-1).

## 고려한 대안

| 대안 | 기각 이유 |
|---|---|
| 작성자 ID 를 암호화해 `posts` 에 저장 (키는 서버만) | 키 관리가 생기고, 암호문이 같으면 같은 작성자임이 드러난다(결정적 암호화). 랜덤 암호화면 빈도 제한·본인 글 조회가 서버 왕복을 필요로 한다 |
| 작성자를 저장하지 않음 (완전 익명) | 본인 글 수정·삭제(M-7), 교환(X-*), 빈도 제한(M-9), 반복 위반 제재(POL-3-10)가 불가능 |
| 애플리케이션 서버가 모든 읽기를 대행 | 무료 티어·소규모 개발에 비해 운영 부담. RLS 로 충분히 표현 가능 |

## 결과

- 좋은 점: 보장이 코드 리뷰가 아니라 DB 권한 검사로 확인된다(TC-PR-01 이 SQL 한 줄). 클라이언트 버그가 익명성을 깨지 못한다.
- 나쁜 점: `select=*` 를 쓸 수 없다(컬럼 GRANT). 정의자 뷰가 늘어 Supabase 보안 점검기 경고가 생긴다 — 의도적임을 주석으로 남긴다.
- 남는 위험: 프로젝트 소유자, 플랫폼 로그. 운영 규칙으로 관리한다.
