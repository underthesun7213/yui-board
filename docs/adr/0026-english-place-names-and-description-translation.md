## 배경

**이름.** 지금 장소 이름은 쓴 사람의 언어 그대로다. 테스트 고정 데이터만 봐도 `枚方市駅`, `만다이 히라카타점`, `FamilyMart` 가 한 지도에 섞인다. 한국어 사용자는 일본어 이름을, 일본어 사용자는 한글 이름을 읽지 못한다. 이름은 핀 툴팁·목록·카드에 가장 많이 보이는 글이다.

**설명.** 설명(0~500자)은 길어서 언어가 다르면 내용을 알 수 없다. PRD 는 "번역하지 않음 + 언어 표시"(Q-Y4, Y-C5)를 **제안**했고, 책임자는 2026-10-26 대화에서 번역하기로 정했다(D32).

**이전 설계에서 배운 것.** [ADR-0002](0002-write-path-and-translation.md)(보류)는 Edge Function 이 쓰기를 대신 받아 번역한 뒤 `service_role` 로 `p_author` 를 넘겨 저장했다. v2 에서는 그 길을 쓸 수 없다.
- v2 의 원칙은 "규칙은 DB 에만"이다(CLAUDE.md, ADR-0021). 쓰기는 정의자 함수가 `auth.uid()` 로 작성자를 정하고 같은 트랜잭션에서 모든 검사를 한다.
- 쓰기 앞에 서버 코드를 두면 작성자를 넘기는 두 번째 권한 모델이 생긴다. 번역 왕복만큼 쓰기도 느려진다.
- ADR-0002 가 `pg_net` 비동기를 기각한 이유는 둘이었다. "번역 전 본문이 먼저 공개된다"는 v2 에서 문제가 아니다 — 원문을 보여 주는 것이 지금 동작이다. "키가 DB 에 저장된다"는 아래 결정 B5 로 피한다. 번역 키는 Edge Function 비밀값에만 두고, DB 에는 깨우기 신호용 비밀만 둔다.

## 결정 A — 장소 이름 (D31)

1. **이름은 영어 한 칸이다.** 지금의 `name` 열 하나를 그대로 쓴다. 언어별 이름 열도, 일본어 이름 열도 두지 않는다.
2. **쓰는 규칙(안내):** 고유명사는 소리대로(万代 → "Mandai", 枚方 → "Hirakata"), 일반명사는 뜻대로(駅 → "Station", 市役所 → "City Hall", スーパー → "Supermarket"). 현장에서 도움이 되면 일본어를 괄호로 붙인다(예 "Academic Affairs Office (教務課)"). 현장의 일본어 이름은 **Google 지도 링크**(선택 칸, 이미 있음)와 **핀 위치**가 준다.
3. **가벼운 서버 강제:** 이름에 **ASCII 라틴 글자(A–Z, a–z)가 1개 이상** 있어야 한다. 한국어만·일본어만인 이름은 거절되고, "Academic Affairs Office (教務課)" 는 통과한다. 글자 수·제어 문자 같은 다른 규칙은 그대로(1~60자).
   - DB: `create_place`·`update_place` 가 `check_text` 다음에 검사해 `{status:'invalid', field:'name_latin'}` 을 돌려준다(예외가 아님 — IP 카운트 보존, RFC-0003 §13.1 4). `app.places` 에 CHECK 를 마지막 방어선으로 더한다. 범위식 `[A-Za-z]` 는 정렬 규칙에 따라 해석이 달라질 수 있어 52글자를 그대로 나열한다(ERD v2 §4.1).
   - 클라이언트: `src/domain/validation.ts` 의 `checkPlace` 가 같은 검사를 하고 같은 필드 이름(`name_latin`)을 돌려준다. "두 번 검사" 규칙(CLAUDE.md)대로 둘을 함께 바꾸고, 단위 테스트가 같은 입력 세트로 둘의 판정이 같은지 본다(`links.ts` 와 같은 방식).
   - 이것은 "영어로 썼는가"를 보장하지 않는다. "히라카타 T-SITE" 처럼 라틴 글자가 섞인 한국어 이름은 통과한다. 의도한 가벼움이다 — 나머지는 안내 문구와 신고("틀린 정보")에 맡긴다.
4. **이름은 번역하지 않는다.** 번역 파이프라인(결정 B)은 설명만 다룬다.

## 결정 B — 설명 번역 (D32)

1. **사용자 쓰기 경로는 바뀌지 않는다.** `create_place`·`update_place` 는 지금처럼 원문만 저장하고 작성자는 `auth.uid()` 다. 쓰기 앞에 Edge Function 을 두지 않는다.
2. **번역은 저장 뒤에 비동기로 붙인다.**
   - ① `app.places` 의 트리거가 같은 트랜잭션에서 **작업 대기열 `app.translation_jobs`** 에 한 행을 넣는다. 설명이 바뀔 때만 넣고, 옛 번역은 그 자리에서 지운다.
   - ② `pg_cron`(1분마다)이 `app.translation_kick()` 을 부른다. 이 함수는 할 일이 있을 때만 `pg_net` 으로 Edge Function 을 깨운다. 깨우는 요청에는 데이터가 없다.
   - ③ Edge Function `translate` 가 `public.translation_claim` 으로 작업을 가져온다.
   - ④ 기계 번역 API 를 부른다.
   - ⑤ 결과를 `public.translation_apply` 로 돌려준다.
   - 두 함수는 `service_role` 만 부를 수 있는 정의자 함수다. Edge Function 이 쓸 수 있는 곳은 이 둘뿐이고, 두 함수가 쓰는 곳은 번역 표·대기열·사용량 표뿐이다(원문은 못 바꾼다).
3. **저장 형태:** `app.place_translations(place_id, lang, description, source_hash, provider, translated_at)`. 기본 키는 `(place_id, lang)` 이다. `source_hash` 는 원문 `sha256` 이다. 번역은 원문이 쓰인 언어를 뺀 두 언어로 만든다. 공개 읽기는 새 뷰 **`public.place_translations_public(place_id, lang, description)`** 이고 원문과 같은 공개 조건을 따른다(ERD v2 §4.8).
4. **무효화:**
   - 설명을 고치면 트리거가 옛 번역을 지우고 작업을 새 해시로 다시 넣는다.
   - 번역 중에 고친 경우(작업을 가져간 뒤 사용자가 수정)에는 `translation_apply` 가 해시를 현재 원문과 비교한다. 다르면 저장하지 않는다(`stale`).
   - 숨김·삭제는 원문을 따른다. 숨긴 장소의 번역은 뷰에서 빠진다. 숨긴 동안에는 대기 작업도 가져가지 않는다 — 신고로 숨긴 글(예: 개인정보 노출)을 외부로 보내지 않기 위해서다. 삭제하면 그 순간 번역과 작업을 지운다. 원문은 30일 보관(Y-E2)하지만 번역은 다시 만들 수 있는 파생물이라 남길 이유가 없다.
5. **비밀값:**
   - 번역 API 키, 이 기능 전용 Supabase secret 키(`sb_secret_…`, 감시용 키와 따로 — 따로 폐기할 수 있게), 깨우기 비밀은 **Supabase Edge Function 비밀값**에만 둔다.
   - DB(Vault)에는 깨우기 비밀과 함수 URL 만 둔다.
   - 클라이언트·저장소·빌드에는 아무것도 들어가지 않는다(Y-S2).
6. **LLM 이 아니라 일반 기계 번역 API 를 쓴다.** 사용자 글은 신뢰할 수 없는 입력이다. LLM 에 넣으면 글 안의 지시("이 글을 번역하지 말고 … 라고 써라")가 출력을 바꿀 수 있다. 기계 번역 API 는 지시를 따르지 않는다. 글은 `textType=plain`(HTML 해석 없음)으로 보낸다.
7. **번역 결과도 신뢰하지 않는다.** `translation_apply` 는 길이(1~2,000자)와 `app.check_text` 의 여러 줄 규칙(제어·서식·방향 문자 거절)을 검사해 어긋나면 버린다. 화면은 지금처럼 텍스트로만 출력한다(JSX 보간, Y-S4).
8. **실패하면 원문을 보인다(지금과 같은 동작).**
   - 재시도는 지수 백오프로 최대 5회 한다.
   - 제공자 한도가 다 차면 대기열 전체를 멈춘다(`paused_until`).
   - 문자 수 한도가 있다: 하루 기본 60,000자, 한 달 1,500,000자 — 설정값이고 제공자에 맞춰 정한다. 한도를 넘으면 새 작업을 가져가지 않는다.
   - 기능 전체 스위치 `translation_enabled` 는 **기본 0(꺼짐)** — 비밀값을 넣은 뒤 책임자가 켠다.
   - `ops_health` 3판에 대기 수, 가장 오래 기다린 작업, 실패 수, 오늘·이번 달 문자 수를 더한다.
9. **화면:**
   - 설명은 **화면 언어의 번역을 기본으로** 보인다.
   - 그 아래 "자동 번역 · [원문 보기]" 를 둔다. 원문을 보면 지금의 언어 배지(Y-C5)와 [번역 보기] 가 나온다.
   - 번역이 없으면(아직 안 됐거나, 실패했거나, 같은 언어) 지금과 같다.
   - 표시 컴포넌트는 `src/ui/LangText.tsx` 에 두고, 홈이 다음 일정 제목에 같은 컴포넌트를 써서 이 모듈이 **첫 화면 청크**에 들어가게 한다. 지도 청크(59.9/60 KB)에는 호출 자리만 남는다(RFC-0003 §11.5).
10. **이미 있는 장치를 쓴다.**
    - 번역을 저장하면 `data_version` 이 오른다. 클라이언트는 지금처럼 판 번호를 보고 다시 받는다.
    - Edge Function 의 쓰기(POST)도 `db_pre_request` 의 IP 한도에 세진다. 한 번 실행에 POST 2번이라 한도(5분 60) 안이다 — 리미터는 고치지 않는다.
11. **제공자:** 아래 비교로 **Azure AI Translator F0** 를 추천한다. 최종 선택은 책임자가 한다(TR-Q1). 코드는 `translate(texts, to[]) → {text, detected}[]` 어댑터 하나 뒤에 두어 교체가 한 파일이다(ADR-0002 결정 5 의 방식만 이어받음).
12. **개인정보:** 사용자 글이 번역 제공자에게 간다. 개인정보처리방침에 **처리 위탁처(번역 제공자)와 해외 이전** 행을 더해야 하고, 이것을 **첫 번역을 보내기 전에** 게시해야 한다(RFC-0003 §16). 보내는 것은 설명 원문뿐이다. 장소 id·좌표·작성자·IP 는 보내지 않는다.

- 데이터 사용 조건(No Trace)이 무료 등급에도 적용된다.
- 한도를 넘어도 돈이 나가지 않는다.
- 무료 한도가 예상 사용량(*추정*: 첫 학기 장소 300곳 × 평균 120자 × 두 언어 ≈ 72,000자, 이후 월 수만 자)보다 훨씬 크다.

나머지 둘은 이렇게 본다.
- **Google:** 조건은 괜찮다. 넘으면 과금되므로 할당량 상한을 직접 걸어야 한다.
- **DeepL 무료 판:** 조건이 "개인정보가 든 글 금지·학습 사용"이라 맞지 않는다. 사용자 설명에는 실수로 개인정보가 들어갈 수 있다(Y-M7 이 경고하는 이유). DeepL 을 쓴다면 유료 판이어야 한다.

품질은 책임자가 실제 장소 설명 20개쯤으로 세 제공자를 블라인드 비교해 정하기를 권한다(TR-Q1).

## 고려한 대안

| 대안 | 기각 이유 |
|---|---|
| **언어별 이름 열**(`name_en`·`name_ja`·`name_ko`) | 쓰는 사람이 세 언어를 알아야 하거나, 이름까지 기계 번역해야 한다. 고유명사의 기계 번역은 자주 틀린다(万代 → "Bandai"/"ten thousand generations"). 칸이 셋이면 검증·신고·관리 화면도 세 배가 된다. D31 은 한 칸을 정했다 |
| **일본어 이름 열**(영어 + 현장 표기) | Google 지도 링크와 핀이 같은 역할을 한다. 칸이 하나 늘면 검증·노출 면도 는다(Y-S12). 필요한 사람은 괄호로 쓸 수 있다 |
| **로마자 변환을 자동으로 만들기**(일본어 이름 → Hepburn) | 한자 읽기는 문맥에 따라 다르다(枚方 = Hirakata 인데 기계적으로 읽으면 "Maikata"). 정확하게 하려면 사전·형태소 분석기가 필요하다. 일반명사는 뜻으로 옮기라는 D31 규칙(駅 → Station)도 따르지 못한다 |
| **이름 규칙 없이 안내만** | D31 이 가벼운 강제를 정했다. 강제가 없으면 한글·한자만인 이름이 계속 들어온다 |
| **이름 규칙을 더 세게**(라틴 글자 비율, 한글·가나 금지) | 괄호 안 일본어(D31 이 허용)를 막거나 판정이 복잡해진다. "가볍게"가 결정이다 |
| **쓰기 전에 번역**(ADR-0002 — Edge Function 이 쓰기를 받아 번역 후 `service_role` 로 저장) | "규칙은 DB 에만"과 충돌하고, 작성자를 넘기는 두 번째 권한 모델이 생긴다. 쓰기가 번역 왕복만큼 느려지고, 번역 장애가 쓰기 장애가 된다 |
| **LLM 번역**(Claude·GPT 류) | 글 안의 지시를 따를 수 있다(프롬프트 주입). 출력 형식·길이도 보장되지 않는다. 비용·데이터 조건도 제공자마다 따로 봐야 한다. 기계 번역 API 로 충분하다 |
| **브라우저 안 번역**(Chrome Translator API 등) | 데스크톱 Chrome 138+ 에만 있고 모바일·Safari 는 지원하지 않는다([Chrome 문서](https://developer.chrome.com/docs/ai/translator-api)). 사용자 대부분이 휴대폰이라 대부분에게 번역이 없다. 브라우저 자체 페이지 번역은 지금도 사용자가 쓸 수 있다 |
| **읽을 때 번역 + 캐시**(요청이 오면 번역) | 읽기는 계정 없이 열려 있다(Y-A1). 읽기 요청이 번역 비용을 부르면 외부 공격자가 비용을 태울 수 있다(T-20 과 같은 구조). 저장 뒤 한 번 번역하면 비용 상한이 쓰기 한도에 묶인다 |
| **Database Webhook 으로 행마다 바로 호출** | 위 "깨우는 방식 비교" |
| **번역 키를 DB(Vault)에 두고 `pg_net` 이 제공자를 직접 호출** | 제공자 응답 처리(배치·오류·감지 언어)를 SQL 로 써야 한다. `pg_net` 응답은 비동기라 결과를 다시 읽는 작업이 또 필요하다. 키가 DB 에 있으면 DB 백업에 키가 들어간다 |
| **`translation_apply` 를 거치지 않고 Edge Function 이 표에 직접 씀** | `service_role` 에 표 권한을 줘야 한다(V-1·checks ② 위반). 검증이 DB 밖으로 나간다 |

## 결과

**좋은 점**
- 사용자 쓰기 경로·권한 모델·작성자 결정이 그대로다. 번역이 늦거나 망가져도 쓰기와 원문 읽기는 영향이 없다.
- 새 권한은 `service_role` 의 함수 둘뿐이다. 두 함수가 쓸 수 있는 곳이 정해져 있고, 카탈로그 검사(checks ⑩)가 목록을 고정한다.
- 비용 상한이 DB 설정값 하나다. F0 등급에서는 상한을 잘못 잡아도 과금이 없다.
- 이름이 한 언어라 지도·목록을 누구나 읽는다. 관리자 검색(Y-P7)도 쉬워진다.

**나쁜 점**
- 움직이는 부품이 넷 는다: Edge Function 하나, 확장 하나(`pg_net`), 예약 작업 하나, 외부 사업자 하나. 로컬 스택에는 Edge Function 런타임·`pg_cron`·`pg_net`·Vault 가 없어 **깨우는 부분은 클라우드에서만 확인된다**(RFC-0003 §19.1a, §17.6a PL-7).
- 번역은 등록 뒤 1~2분 걸린다. 그동안 다른 사람에게는 원문이 보인다.
- 번역이 들어올 때마다 `data_version` 이 올라 열린 클라이언트가 전체를 다시 받는다. 쓰기 한 번당 다시 받기가 약 두 번이 된다. 출시 뒤 일괄 번역 동안은 실행 간격을 늘려 줄인다(RFC-0003 §11.4).
- 작성 언어(`lang`)를 잘못 고르면 그 언어 사용자에게는 번역이 없을 수 있다. 예: 일본어로 쓰고 "한국어"를 고르면, 한국어 화면은 "같은 언어"로 보고 원문을 보여 준다. 원문 보기·언어 배지로 남는 위험이다.
- 고유명사·지명이 설명 안에서 잘못 번역될 수 있다. "원문 보기"가 대응이다.
- 개인정보처리방침이 바뀌어야 한다(위탁·해외 이전).
- 이름 규칙 때문에 테스트 고정 데이터(`tests/fixtures/places.json`, `supabase/seed/fixtures.sql`)의 한국어·일본어 이름을 바꿔야 한다. 그대로 두면 seed 가 새 CHECK 에서 실패한다.

**영향 범위(구현 때 바뀌는 것 — 이 ADR 은 코드를 바꾸지 않았다)**

| 층 | 파일 |
|---|---|
| DB | 새 마이그레이션 둘: `…_place_name_latin.sql`(함수 2개 교체 + CHECK), `…_translations.sql`(표 4개, 트리거, 뷰, 함수 3개, 설정, 예약, 권한, 자기 검사). `ops_health` 3판. 이미 적용된 `…_checks.sql` 은 고치지 않는다(이유는 ERD v2 §8 24) |
| Edge Function | `supabase/functions/translate/`(Deno): `index.ts`(진입·비밀 확인), `core.ts`(Deno API 없는 순수 로직 — Vitest 대상), `providers/azure.ts` 등 |
| 클라이언트 | `src/domain/validation.ts`(이름 규칙), `src/api/rest.ts`(번역 뷰 읽기), `src/api/errors.ts`(`name_latin`), `src/state/data.ts`(번역 맵·스냅샷), `src/domain/types.ts`, `src/ui/LangText.tsx`(`UserText`), `src/features/map/MapScreen.tsx`(카드), `src/features/home/Home.tsx`(다음 일정 제목), `src/features/write/PlaceForm.tsx`(이름 안내), `src/i18n/{en,ja,ko}.ts` |

**출시 전에 넣을 때와 뒤에 넣을 때 (TR-Q3)**

| | 출시 전 | 출시 뒤 |
|---|---|---|
| 방침 | 첫 게시부터 위탁·해외 이전 행 포함 | 방침을 고쳐 공지한 **뒤에** 번역을 켠다. 이미 받은 글을 새 위탁처로 보내는 것이라 공지가 먼저다(공지 기간은 법무 검토) |
| 기존 글 | 없음(운영 DB 에 실제 데이터 0) | 마이그레이션이 보이는 장소 중 설명이 있는 것을 모두 대기열에 넣는다. 하루 문자 한도가 일괄 번역을 며칠로 나눈다. 1,000곳 × 120자 × 2 ≈ 240,000자(*추정*) — F0 한도 안 |
| 기존 이름 | 없음 | 라틴 글자가 없는 이름이 남아 있다. CHECK 는 `not valid` 로 넣는다. 함수는 **이름을 바꿀 때만** 규칙을 적용한다 — 설명만 고치는 등록자를 막지 않는다. 관리자가 정리한 뒤 `validate constraint` |
| 반영 부담 | 없음 | 일괄 번역 동안 `data_version` 이 자주 올라 열린 클라이언트가 자주 다시 받는다 → 그 기간에는 실행 간격을 5분, 한 번에 100건으로 |
| 순서 | — | DB 마이그레이션 → 클라이언트 배포(새 뷰가 먼저 있어야 함, RFC-0003 §19.2 순서 규칙) → 방침 공지 → 비밀값·스위치 ON |
