# ADR-0007 · 지표는 사용자 ID 없는 일별 카운터로만 모은다

| | |
|---|---|
| 상태 | 제안됨 |
| 날짜 | 2026-10-11 |
| 근거 | PRD §11, Q10, POL-5-7, 출시 계획 §3, BL-35 |
| 관련 | [ERD §4.5](../architecture/erd.md#45-지표-adr-0007), ADR-0001 |

## 배경

PRD §11 의 지표 중 "주간 활성 입주자", "비원어 열람 비율", "원문 보기 사용률", "일본어 완독"은 조회 기록이 필요하다. 조회 로그(누가 언제 무엇을 봤는지)는 익명성 원칙과 충돌한다(POL-5-7). 출시 계획 §3 은 `weekly_opens`, `daily_views` 같은 카운터를 제안했지만 스키마에 없다.

## 결정

1. 테이블 하나 `metric_daily(day, metric, dim1, dim2, n)` 를 둔다. **사용자 ID, 기기 ID, 글 ID 를 저장하지 않는다.** `day` 는 Asia/Tokyo 날짜.
2. 클라이언트는 `bump_metric(metric, dim1, dim2)` RPC 로 1 을 더한다(`authenticated` 만). 함수는 허용 목록 밖의 지표·차원을 조용히 무시한다.

   | metric | dim1 | dim2 | 언제 |
   |---|---|---|---|
   | `open_week` | ISO 주 | — | 기기가 그 주에 처음 앱을 열 때 (`localStorage` 플래그) |
   | `view_detail` | 원문 언어 | 보기 언어 | 글 상세 열기 |
   | `view_original` | 원문 언어 | 보기 언어 | "원문 보기" 누름 |
   | `lesson_done` | 에피소드 id | — | 마지막 컷 도달 또는 엔딩 |
   | `tr_chars` | — | — | Edge Function 이 번역 글자 수를 더함 (service) |

3. 그 밖의 지표(주간 신규 글, 숨김 비율, 신고 처리 시간, 교환 성사율)는 기존 테이블의 **집계 쿼리**로 계산한다. 대시보드는 운영자용 SQL 뷰(출시 계획 §3).
4. 외부 분석 도구(GA 등)는 쓰지 않는다.

## 고려한 대안

| 대안 | 기각 이유 |
|---|---|
| 조회 로그 테이블(사용자 ID 포함) + 집계 후 삭제 | 삭제 전까지 열람 기록이 존재. 작성자 테이블과 대조하면 행동 프로파일 |
| `auth.users.last_sign_in_at` 으로 활성 측정 | 로그인할 때만 바뀌어 활성과 다르다(출시 계획 §3) |
| 외부 분석 서비스 | 제3자 전송, 비용, 개인정보처리방침 부담 |

## 결과

- 좋은 점: 익명성과 충돌하지 않는다. 테이블 하나, RPC 하나.
- 나쁜 점: 클라이언트가 카운터를 부풀릴 수 있다(입주자만 가능, 영향은 지표 왜곡뿐). 기기 기준이라 한 사람의 두 기기는 둘로 센다. 근사치임을 대시보드에 표시한다.
- 확인: 일 단위 집계에서 새벽 시간대처럼 사용자가 적으면 "그날 누가 원문을 봤나"를 추정할 여지가 이론상 있다. 시간 단위로 쪼개지 않는다.

## 열린 질문

| # | 질문 |
|---|---|
| G-Q1 | 지표 카운터 호출을 동의(옵트인/옵트아웃) 대상으로 할 것인가 — 개인정보처리방침(POL-5-6)에 쓸 내용 |
| G-Q2 | 대시보드 접근 권한: 운영자(RA) 전원인가, 관리자만인가 (출시 계획 §4) |
| G-Q3 | 번역 한도 소진 표시(`tr_quota_out`, RFC §5.2)를 이 테이블에 둘지 별도 설정 테이블에 둘지 |
| G-Q4 | 카운터 부풀리기를 막기 위한 상한(예: 한 요청당 1, 하루 지표별 전체 상한)이 필요한가 |
