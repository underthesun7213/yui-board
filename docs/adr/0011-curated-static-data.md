# ADR-0011 · 장소·일정은 직접 넣은 정적 데이터로 두고 런타임 검색을 쓰지 않는다

| | |
|---|---|
| 상태 | 제안됨 |
| 날짜 | 2026-10-12 |
| 근거 | PRD-MLP D6, ML-M8, ML-K6, ML-K7, ML-P1~P4, §3 비목표 "장소 자동 검색 (OSM Overpass 등)", Q-M8, Q-M11 |
| 관련 | [RFC-0002 §10](../architecture/rfc/0002-mlp-client-only.md#10-데이터-형식--2차-장소일정-현행--adr-0011), ADR-0009, ADR-0012 |

## 배경

지도는 "내 주위" 와 "일본 전체" 를 보여 준다(D4, D5). 1차 데이터는 結 주변 13곳이라 다른 지역에서는 지도가 빈다(PRD §12). 빈 지도를 채우는 방법으로 런타임 검색(OSM Overpass API, Google Places)이 떠올랐다. 책임자는 "직접 넣은 데이터만" 으로 정했다(D6, 그 뒤 재확인). 이 ADR 은 그 결정의 기술적 근거와 데이터 형식을 기록한다. 일정도 서버가 없으므로 같은 방식이다(ML-K6).

## 결정 (현행 구현과 같다)

1. 장소는 `index.html` 의 `PLACES` 배열, 일정은 `EVENTS` 배열에 **사람이 직접 넣는다.** 갱신 = 배열 수정 → 커밋 → `sw.js` 의 `CACHE` 올림 → 배포.
2. 장소 형식: `id`, `pref`(JIS X 0401 2자리), `cat`(6종), `lat`, `lng`, `n{ja,en,ko}` 필수, `d{…}`, `by`, `gid` 선택. 도보 시간은 저장하지 않고 기준점에서 계산한다.
3. 일정 형식: `id`, `kind`, `d`, `time`, `end`, `host`, `place`, `t`, `b` 필수, 매주 반복은 `weekly.until` 로 한 번만 적고 `over[date]` 로 회차별 제목·설명을 덮어쓰거나 `over[date]={cancel:true}` 로 그 회차를 뺀다.
4. 런타임에 외부 장소 검색 API 를 부르지 않는다. 지도의 외부 요청은 타일뿐이다.
5. Google 지도는 API 가 아니라 **딥 링크**(`place_id`)로만 연결한다(README "No Google Maps API").
6. 손으로 넣은 데이터는 CLAUDE.md 헤드리스 검사가 배포 전에 확인한다: 일정의 id 중복·`host`·날짜·시각 형식·3개 언어, 장소의 id 중복·`cat`·`pref`·좌표·`by`·3개 언어 (코드 리뷰 뒤 추가 — `78e2b4e`, 일정 id 중복은 그 뒤 `7b6d631` 까지 사이).

## 고려한 대안

| 대안 | 장점 | 단점 / 기각 이유 |
|---|---|---|
| **OSM Overpass API 를 런타임에** | 일본 어디서나 편의점·역·병원이 바로 보인다 | (1) **이용 조건:** 공개 주 인스턴스는 "하루 약 10,000 요청, 1 GB 이하" 를 안전선으로 제시하고, 정기적으로 쓰는 설정은 그 수치를 100 으로 나누라고 한다(하루 100 요청·10 MB). 상업적 사용은 자체·유료 서버를 쓰라고 한다. 식별 가능한 User-Agent/Referer, 캐시, 429 뒤 대기도 요구한다 ([Overpass API — OSM Wiki](https://wiki.openstreetmap.org/wiki/Overpass_API), [Overpass API User's Manual](https://dev.overpass-api.de/overpass-doc/en/preface/commons.html), 2026-10-12 검색 확인). 650명이 지도를 열 때마다 질의하면 "정기 사용" 기준을 넘을 수 있다. (2) **개인정보:** 질의 범위가 사용자 주변 좌표라 위치가 제3자 서버로 간다 — ML-P2 "좌표를 어디로도 보내지 않는다" 위반. (3) 품질: 이름이 일본어·로마자 위주라 3개 언어 설명·"추가한 사람" 같은 큐레이션 정보가 없다. 이 앱의 가치는 "입주자가 실제로 쓰는 곳" 이다. (4) 오프라인 불가 |
| Overpass 를 **개발 때 한 번** 돌려 후보를 뽑고 사람이 고름 | 2차 데이터 수집을 돕는다. 런타임 요청 없음 | 가져온 데이터가 OSM 유래면 ODbL 저작자 표시·공유 조건을 따져야 한다(*확인 필요*). 수집 도구로는 열어 둔다 — 결정 1~4 와 충돌하지 않는다 |
| Google Places API | 품질·다국어 | API 키·과금·이용 약관(캐시 제한 등, *미확인*), 위치가 Google 로 감, 서버 없는 클라이언트에 키를 노출. README 결정과 충돌 |
| 데이터를 별도 JSON(`data/places.json`, `data/events.json`)으로 | `index.html` 이 데이터로 비대해지지 않는다. 데이터 담당자가 코드를 안 만진다 | fetch·로딩 상태·실패 처리가 생긴다. 헤드리스 검사가 데이터를 따로 읽어야 한다. 지금 13곳·일정 6건에서는 이점이 작다 → **2차 데이터 규모를 보고 결정**(열린 질문) |
| 공유 스프레드시트·캘린더 피드에서 런타임으로 | 배포 없이 갱신 | 제3자 의존, 오프라인·검사 복잡, 갱신 담당 미정(Q-M11) — ADR-0009 대안과 같음 |

## 결과

- 좋은 점: 외부 요청·키·과금 없음. 오프라인에서 목록·카드·도보 추정 모두 동작. 데이터가 코드와 함께 버전 관리되고 헤드리스 검사가 실제 데이터로 뷰를 그린다.
- 나쁜 점: 갱신에 커밋 권한이 필요하다. 결 주변 밖은 데이터가 생길 때까지 비어 있다(빈 상태 문구 ML-M7, "내 주위" 빈 문구).
- **해결:** 이 ADR 첫 판의 "형식 검사가 없어 오타 하나가 화면을 깨뜨릴 수 있다(특히 일정 `host` 오타 → 캘린더 전체 예외)" 는 결정 6 의 헤드리스 데이터 검사로 해결됐다. 일정 id 중복도 이제 검사한다. 남은 작은 공백(`weekly.until`·`kind` 값, `end > time`)은 RFC-0002 §10.3.
- 3개 언어를 다 못 채운 2차 데이터(Q-M8)는 이제 검사에서 실패한다(배포 전에 막힘). 화면 쪽 폴백은 없다 — 한 언어로만 온 데이터는 번역해 넣어야 한다.

| D-Q1 | 2차 데이터가 몇 건인가 — 수백 건이면 `data/*.json` 으로 분리 (뷰 순수성은 유지, 로드는 시작 코드) |
