## 1. 배경

**GLOBAL COMMONS 結 -YUI-** 는 간사이외대 고텐야마 캠퍼스의 국제 기숙사다. 입주자는 약 650명이고,
일본인 학생과 교환학생이 유닛을 함께 쓴다.

입주자에게 필요한 정보는 지금 Instagram DM, 게시판 종이, 입소문에 흩어져 있다. 그리고 교환학생이
바뀔 때마다 그 정보가 통째로 사라진다. 한 입주자가 알아낸 것을 다음 입주자도 볼 수 있게 남기는
것이 이 제품의 목적이다.

## 2. 문제 정의

1. **정보가 흩어져 있다.** 행사, 고장 신고, 중고 거래, 분실물이 서로 다른 채널에 있다.
2. **정보가 학기마다 사라진다.** 교환학생이 바뀌면 동네 정보와 생활 요령을 처음부터 다시 배워야 한다.
3. **언어가 세 개다.** 일본어, 영어, 한국어 화자가 한 건물에 살지만 서로의 글을 읽기 어렵다.
4. **공동생활이라 실명으로 말하기 어렵다.** "3층 키친 프라이팬 좀 치워주세요" 같은 말은 익명이어야 나온다.
   반대로 익명은 특정인 저격으로 번지기 쉽다.

## 3. 목표 / 비목표

### 목표

- G1. 입주자 생활 정보를 **네 곳**(게시판, 캘린더, 일본어, 지도)에 모은다.
- G2. 모든 글을 **세 언어**로 읽을 수 있게 한다. 원문은 언제든 볼 수 있어야 한다.
- G3. **구조적 익명성**을 보장한다. 운영자를 포함해 클라이언트에서는 글쓴이를 알아낼 수 없어야 한다.
- G4. 익명 공간의 부작용을 **신고 → 운영자 검토**로 관리한다. 운영자의 조치는 기록이 남는다.
- G5. 거래처럼 연락이 필요한 경우에만, **양쪽이 동의**하면 신원을 교환한다.
- G6. 설치 가능한 모바일 웹앱(PWA)으로 제공하고, 운영비는 0에 가깝게 유지한다.

### 비목표 (이번 범위 아님)

- 1:1 채팅, 실시간 메시징
- 기숙사 공식 시스템(예약, 출입, 공지 시스템) 대체·연동
- 네이티브 앱 (iOS/Android 스토어 배포)
- 기숙사 외부 사용자 지원
- 결제, 에스크로 등 거래 중개

## 4. 사용자

| 역할 | 설명 | 핵심 니즈 |
|---|---|---|
| 일본인 입주자 | 장기 거주, 일본어 모국어 | 생활 불편 공유, 교환학생과 교류 |
| 교환학생 | 1~2학기 거주, 영어·한국어 등 | 동네 정보, 생활 일본어, 행사 참여, 귀국 전 물건 처분 |
| RA (Resident Assistant) | 유닛 단위 관리 입주자 | 유닛 행사 공지, 신고 처리 |
| 운영자 (사무실 / GIP) | 기숙사 사무실, Global Innovation Program | 공식 행사 공지, 장소 정보 관리 |

## 5. 현재 상태

`index.html` 은 **mock data 로 동작하는 모바일 프로토타입**이다. 백엔드가 없고, 작성한 글은 새로고침하면
사라진다. `schema.sql` 은 Supabase/Postgres 설계안이며 아직 어디에도 적용되지 않았다.

이 PRD는 프로토타입에서 확인된 기능을 요구사항으로 정리하고, 실제 서비스로 가기 위한 백엔드
요구사항과 미결 사항을 함께 적는다.

## 7. 익명성·개인정보 요구사항

이 제품의 핵심 신뢰 장치다. 기능보다 우선한다.

| ID | 요구사항 |
|---|---|
| PR-1 | 글·댓글의 본문 테이블과 작성자 테이블을 분리한다 (`posts` ↔ `post_authors`, `comments` ↔ `comment_authors`) |
| PR-2 | 작성자 테이블은 RLS 활성 + 정책 0개. PostgREST(anon/authenticated)로는 읽을 수 없고 `service_role` 연결만 읽을 수 있다 |
| PR-3 | **작성자가 있는 콘텐츠**(글·댓글)는 `SECURITY DEFINER` 함수(`create_post`, `add_comment`)로만 작성한다. 본문과 작성자 행이 한 트랜잭션에 들어간다. 글·댓글에 대한 직접 INSERT 정책은 없다 (좋아요·신고·RSVP 는 본인 행 직접 INSERT 허용) |
| PR-4 | `service_role` 키는 클라이언트에 절대 포함하지 않는다 |
| PR-5 | 신고자 ID는 저장하지만 어떤 뷰·정책으로도 조회되지 않는다. 운영자는 `report_queue`(대상·사유·건수)만 본다 |
| PR-6 | 운영자는 익명이 아니다. 모든 숨김/복원/유지 조치는 `mod_actions` 에 운영자 ID와 함께 기록된다 |

**검증 방법:** 스키마 적용 후 `authenticated` 역할로 다음을 확인하는 테스트를 둔다.

- 다른 사용자의 `profiles` 행이 보이지 않음
- `UPDATE profiles SET is_admin = true` → 실패
- 같은 작성자의 두 글에 교환 요청 → 다른 작성자의 두 글과 구별되는 반응이 없음
- 운영자가 `posts.hidden_at` 직접 수정, `mod_actions` 수정·삭제 → 실패

## 9. 시스템 구성 (목표)

```
[PWA: index.html] ──(anon key, 사용자 JWT)──> [Supabase PostgREST]  읽기: RLS 적용 테이블·뷰
        │                                              ↑
        └──(글/댓글 작성)──> [서버 함수] ──번역──> [Azure Translator]
                                   └──(service_role, p_author 명시)──> create_post / add_comment
```

- 읽기는 클라이언트가 RLS 아래에서 직접 한다.
- 작성은 서버가 사용자 JWT 를 검증하고 번역을 끝낸 뒤 `service_role` 로 `SECURITY DEFINER` 함수를 호출한다. 클라이언트는 작성 함수를 직접 호출할 수 없다 (§13 Q4).
- 인증: `auth.users` 에 `<room>@yui.local` 형태로 로그인. 방 주인이 바뀌면 auth 행 이름만 바꾼다.
  가입 허용 이메일 도메인은 `allowed_domains` 테이블로 관리한다 (§13 Q3 참조).

## 13. 미결 사항 (결정 필요)

코드를 읽으며 발견한 불일치와 빈칸이다.

| # | 내용 | 근거 |
|---|---|---|
| Q1 | **방 번호 노출 여부가 문서·스키마·UI 사이에서 다르다.** README 와 스키마는 "방 번호는 노출하지 않고 층만 보여준다"인데, 프로토타입의 교환 경고 문구(`exWarn`)·받은 요청·교환 목록은 **방 번호**를 보여준다. 스키마 뷰(`my_contacts`, `my_incoming_requests`)는 층만 준다. 어느 쪽으로 맞출지 결정 필요 | `index.html` `T.*.exWarn`, `profiles()` / `schema.sql` §10 |
| Q2 | **모집(meet) 게시판의 실명 공개 기능.** `T` 에 "이 글은 익명이 아닙니다", 표시 이름·연락처 입력 문자열(`openT`, `openNote`, `fName`, `fContact`, `organizer`, `contactL`)이 3개 언어로 있으나 어디서도 쓰이지 않고, 스키마에도 해당 컬럼이 없다. 기능을 살릴지, 문자열을 지울지 결정 필요 | `index.html` `T` |
| Q3 | **로그인 방식.** 스키마 주석은 `<room>@yui.local` 로그인이라 하고, 동시에 가입 허용 도메인 테이블(`allowed_domains`)이 있다. 학교 이메일 가입인지, 방 계정 발급인지 정해야 한다 | `schema.sql` §1 |
| Q4 | **서버가 작성 함수를 어떤 권한으로 부르는가.** 함수 주석은 "서버에서 번역 후 호출"인데 함수는 `auth.uid()` 를 쓴다. 서버가 `service_role` 로 부르면 `auth.uid()` 가 null 이 된다. 사용자 JWT 를 그대로 넘기면 DB 가 서버와 클라이언트를 구별할 수 없어 S-5 를 막지 못한다. **제안:** 서버는 사용자 JWT 를 검증해 사용자 ID 를 얻고, `service_role` 로 `create_post(p_author uuid, …)` 처럼 작성자를 명시 인자로 넘겨 호출한다. `authenticated` 의 EXECUTE 권한은 회수한다. 함수 안의 `is_resident()` 검사도 `p_author` 기준으로 바꿔야 한다 | `schema.sql` §11 |
| Q5 | **입주자 주최 이벤트를 누가 등록하는가.** 이벤트 종류에 "입주자 주최"가 있지만 `events` 쓰기 정책은 운영자만 허용한다. 입주자 제안 → 운영자 승인 흐름이 필요한지 | `schema.sql` §9 |
| Q6 | **이벤트 정원 검사.** 프로토타입은 클라이언트에서만 정원을 검사하고, 스키마에도 정원 초과를 막는 제약·함수가 없다. 또 `event_rsvps` 에 트리거가 없어 `rsvp_count` 가 갱신되지 않는다. `rsvp` 를 함수로 바꿀지 | `schema.sql` §5, §9 |
| Q7 | **교환 요청 게시판 제한.** UI 는 양도·모집·분실물에서만 허용하지만 `request_exchange()` 는 게시판을 확인하지 않는다 | `schema.sql` `request_exchange` |
| Q8 | **RA 와 운영자의 권한 구분.** 스키마에는 `is_admin` 하나뿐이다. RA 가 자기 유닛만 관리하는지, 전체를 관리하는지 | `schema.sql` `profiles` |
| Q9 | **일본어 컬렉션 저장 위치.** 서버(계정)에 저장할지, 기기(localStorage)에 저장할지. 스키마에 테이블 없음 | `S.cg` |
| Q10 | **지표 측정 방법.** §11 의 "비원어 열람 비율" 등은 조회 로그가 필요하지만 스키마에 없다. 익명성과 충돌하지 않는 집계 방식(사용자 ID 없는 일별 카운터 등)을 정해야 한다 | `schema.sql` |
| Q11 | **RA 권한 부여 절차.** 누가 `is_admin` 을 켜는지, RA 교대 시 회수 절차 | Q8 과 연관 |
